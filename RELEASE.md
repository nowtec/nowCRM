# Release Notes

## 2026-08-03 — v0.0.127

- Fixed API-token authentication at the KrakenD gateway. Strapi stores an API token's `accessKey` as an HMAC-SHA512 digest, but the `token-verify` endpoint compared the incoming token against that digest directly, so the comparison could never match. Every service calling through the gateway with its Strapi API token was rejected with "Token is neither a valid user token nor API token", while the same token worked when sent straight to Strapi. Verification now hashes the token through Strapi's own API-token service and also rejects tokens past their expiry date.
- Wired Strapi's `JWT_SECRET` through the stack as `STRAPI_JWT_SECRET`. It was previously never passed to the container, so Strapi generated one on first boot and wrote it inside the container's own filesystem. Any recreate of the Strapi container — including a routine deployment — produced a new secret and silently invalidated every issued session, signing all users out.
- Wired Strapi's `ENCRYPTION_KEY` through as `STRAPI_ENCRYPTION_KEY`. Without it Strapi logged "Encryption key is missing from config" and stored provider credentials were left unencrypted. `STRAPI_DATABASE_SSL_KEY` is now passed through as well; it existed in the sample environment but never reached the container.
- Removed the `locale` field from seeded demo contacts. Contacts are not a localised content type, so the seeded value landed in Strapi's reserved locale column and made those documents unreachable as relation targets. Creating a task against a seeded contact failed with `Document with id "…", locale "null" not found`, while contacts created through the application worked. Each seeded contact already carried its own `language` value, which is the field that was actually intended.
- `make dev` is now a hot-reloading development environment. It starts the whole stack in Docker, including the CRM on port 3000, and then runs `docker compose watch`. Edits under `apps/` and `libs/` are synced into the running containers and picked up in one to two seconds instead of triggering a full image rebuild. The application services gained a dedicated `dev` Dockerfile target that runs their development servers rather than compiled output, and those images are tagged with a `-dev` suffix so they are never mistaken for production artefacts.
- Backend services are now recreated after Strapi's bootstrap tokens are injected. Composer, Journeys, DAL and Plugins read their API token from the environment when the container is created, so on a first boot they started with an empty token and logged an authorisation failure every minute until they were restarted by hand.
- Added the missing `STRAPI_URL` variable to the CRM's sample environment. The shared services library requires it, so running the CRM outside Docker — the workflow the task runner recommends — failed immediately on environment validation. The trailing slash in the value is significant, because endpoints are resolved relative to it.
- Reorganised the root `.env.sample` into labelled groups with only the comments that carry real information, and reconciled it against the compose files in both directions. Variables that were referenced but never defined (`RABBITMQ_USER`, `RABBITMQ_PASS`, `VERSION`, `TEST_CRM_PORT`, `TEST_USER_USERNAME`, `TEST_USER_PASSWORD`) were added, and dead entries were removed. Six Journeys tuning variables that were documented but never forwarded to the container — job-key lifetimes, the Strapi request timeout and the retry delays — are now passed through, so setting them takes effect.
- Improved the environment bootstrap scripts. New keys added to a sample file are now backfilled into existing `.env` files for the per-service environments as well as the root one, the `CUSTOMER_DOMAIN` placeholder is expanded on every run so that backfilled entries are not left with the literal placeholder, generated files are created with owner-only permissions, and duplicate assignments of the same key are collapsed instead of being written in one place and read from another.
- Moved the workspace to pnpm 11.18.0. Version 11 replaced the `onlyBuiltDependencies` and `ignoredBuiltDependencies` lists with a single `allowBuilds` map, so the build-script permissions for native packages such as sharp, esbuild and `@swc/core` were rewritten in that form, and it now requires an explicit `packages` entry even for a single-package workspace root, which the Strapi application is. The package manager is pinned in both `package.json` files so every environment resolves the same version.
- Stopped the Strapi image from installing a floating package manager. It previously ran `corepack prepare pnpm@latest --activate`, which drifts across pnpm major versions and quietly breaks the build-script allowlist as soon as the key is renamed upstream. The image now enables the pinned version declared by the project.
- Corrected the production bundling filter in the Node service images. `pnpm deploy` was invoked with the directory name (`--filter=journeys`) rather than the workspace package name (`--filter=@nowcrm/journeys`), for Journeys, Composer, DAL and Plugins alike.
- Rebuilt the runtime stages of the Node service images. Each previously inherited from the dependency stage, so the shipped image carried the entire workspace including devDependencies and ran as root. The runtime now starts from a clean `node:22-alpine` containing only the deployed production bundle, runs as the unprivileged `node` user, sets `NODE_ENV=production`, and declares a health check so Compose can gate dependent services on genuine readiness rather than on the container merely having started.
- Split the Strapi image into build and runtime stages. The compilers and headers needed to build sharp stay in the build stage instead of shipping to production, and the admin panel is now built with `NODE_ENV=production` so the optimised bundle is produced.
- Pinned the KrakenD gateway and its plugin toolchain together. The authentication plugin was compiled with a stock Go image while the gateway ran a different KrakenD release; Go plugins are rejected at load time unless they are built with the same toolchain and dependency versions as the host binary. The plugin is now built with `krakend/builder:2.12.1` against the matching `krakend:2.12.1` runtime, and the two tags are documented as needing to move together.
- Tightened `.dockerignore` so build contexts no longer carry local `dist/` and `.strapi/` output, the `.git` directory, coverage reports or Playwright artefacts. A stale local build can no longer shadow what the image compiles from.
- Replaced the YAML anchor templates in all three Compose files with explicit per-service configuration, and named the default network so services no longer need individual network entries. Log rotation and health checks are now declared for every service rather than a subset, and a stray Compose file left inside the wiki application was removed.
- Rewrote the Makefile as the documented entry point for the stack. It gains a help listing, environment bootstrapping, conditional image builds, the hot-reloading `dev` target, log and shell helpers, and cleanup targets, and it checks that Docker and the Compose v2 plugin are actually available before doing anything.
